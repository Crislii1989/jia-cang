# 物品分类：增删改逻辑设计（待你评审）

> 结论先行：分类的「增 / 改 / 删 / 排序」**功能其实早就有**，入口是
> **首页 → 快捷操作「分类管理」**（路由 `/categories`）。
> 但**删除流程目前是坏的**（点删除会抛 SQL 错误），本轮已修好（见文末「已修」）。
> 下面是需要你拍板的 7 个逻辑点，每点都给了我的建议。

---

## 一、现状：数据是怎么连起来的

核心一句话：**物品只记分类的 id，不记分类的名字。**

```
items.category_key  ──►  categories.id
      "sports"              id="sports"  label="运动"  emoji=🏋️
      "custom_1736…"        id="custom_1736…"  label="宠物"
      "membership"          ✗ 不在 categories 表里（虚拟分类，只写在代码常量里）
      ""                    = 未分类（空 key 是「无分类」的唯一表示）
```

由此推出三条**已经成立的好性质**：

1. **改分类名字不会丢分类。** 物品存的是 id，改名只动 `label`，引用不断。
   例：把「运动」改成「健身用品」，所有运动类物品自动跟着显示新名字，**不需要迁移任何数据**。
2. **删分类不能只删那一行**，必须先把引用它的物品重挂，否则物品的 `category_key`
   会指向一个不存在的 id，物品库 / 详情页会显示成一串裸 id（`custom_1736…`）。
3. **重命名是安全的，删除是有破坏性的** —— 这是下面所有讨论的前提。

## 二、现在有「三种」分类，边界不一致 ← 最需要你定

| 类型 | 存在形式 | 数量 | 增 | 改 | 删 | 排序 | 分类管理页 | 物品库 tab | 新增物品「选择分类」 |
|---|---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|:--:|
| **系统分类** | DB 行 `isBuiltIn=true` | 12 | ✗ | ✓ | ✗ | ✗ | ✓ | ✓ | ✓ |
| **自定义分类** | DB 行 `isBuiltIn=false` | 你建的 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| **虚拟分类** | 仅代码常量 | 4 | ✗ | ✗ | ✗ | ✗ | **✗** | ✓ | **✗** |

> 虚拟分类 = 会员订阅 💳 / 网卡流量 📶 / 数字许可证 🔑 / 礼品卡 🎁，
> 由「品类模版」写入，不落数据库。

三处不一致带来的实际后果：

**(a) 虚拟分类不在「选择分类」弹窗里 → 编辑这类物品时分类名会变成裸 id。**
例：用品类模版记的「会员订阅」，`category_key = membership`。
点编辑 → 选择分类弹窗只列数据库分类 → 里面根本找不到「会员订阅」。
**建议**：选择分类弹窗把虚拟分类也列出来，单独一组「订阅与卡券」，可选中但标注不可编辑。

**(b) 虚拟分类不在「分类管理」页 → 用户会疑惑「我明明有会员订阅分类，管理页里却没有」。**
**建议**：管理页补一个「订阅与卡券」分区，只读展示这 4 项 + 各有多少件物品。

**(c) 「数据概览 → 分类数量」只数数据库分类（12 + 自定义），不含虚拟分类。**
而物品库 tab 里是能看到虚拟分类的 → **数字和肉眼所见对不上**。
**建议**二选一（我倾向第 1 个）：
1. 把虚拟分类也算进去，口径统一为「物品库里能看到几个分类」；
2. 保持只数自建分类，但把标签改成「自建分类数」，让口径自洽。

## 三、删除分类时，分类下的物品怎么办？← 请你拍板

现状（已实现，本轮修好）：弹窗提示「该分类下有 N 件物品，删除后物品将变为『未分类』」，
确认后把这 N 件物品的 `category_key` 清空，再删分类。

三个可选方案：

| 方案 | 行为 | 优点 | 代价 |
|---|---|---|---|
| **A. 全变「未分类」**（现状） | 直接清空引用 | 删得干脆，永不卡住 | 若有 100 件物品，它们会集体变未分类，事后一件件补分类非常痛苦 |
| **B. 有物品就不许删** | 报错，必须先清空该分类 | 绝不误伤数据 | 想删分类时被卡住，得先去改物品 |
| **C. 让用户选迁移目标**（我建议） | 弹窗里多一个下拉：「这 N 件物品 → [未分类 / 数码 / 家电 / …]」，选完即迁移 + 删除 | 数据不丢，一步到位 | 弹窗稍复杂 |

**我的建议：C 作默认，并把「未分类」作为下拉里的一个选项**（等于 A 也能选）；
没有物品引用时直接删（现状），不弹窗、不打断。

两个附带细节：
- **无物品时要不要确认？** 现状是直接删。建议**保留**（没有副作用，少一次点击），删完给 toast（已有）。
- **系统分类不可删**这一条建议保留 —— 它们是 AI 识别与品类模版的落点，删了会影响自动归类。
  如果你希望「眼不见为净」，我建议做成**「隐藏」而不是删除**（加一列 `hidden`，
  隐藏后不在 tab 与选择器里出现，但已有引用仍然有效）。这样也顺带解决了「12 个系统分类里有一半用不上」的问题。

## 四、新增分类：入口再顺一点

现状：只能「首页 → 分类管理 → 右上角 +」新建。

**建议**：在**新增 / 编辑物品页的「选择分类」弹窗**底部加一行「＋ 新建分类」，
点开同一套新建弹窗，建完自动选中。

理由：用户是在「给这件物品选分类」的场景里才发现缺分类的。
让他跳出去建、再回来重选，等于把一条流程切成两段。

## 五、校验规则（现在几乎没有）

| 项 | 现状 | 建议 |
|---|---|---|
| 重名 | **允许**（会出现两个「数码」） | **禁止**，提示「已存在同名分类」 |
| 空名 / 纯空格 | 已挡（只判断了非空） | 保持，并去首尾空格 |
| 名称长度 | 无限制 | 限 **8 字**（tab 和卡片会换行/截断） |
| emoji | 有候选库 | 保持 |

**为什么「禁止重名」是硬需求**：`选择分类`弹窗是用「中文名 → id」反查的
（`{label: id}` 映射）。一旦重名，反查会命中**错误的那一个**，
用户看到的分类和实际存进去的 key 可能对不上。这是目前最隐蔽的一个坑。

## 六、排序

现状：系统分类按 `sortOrder` 固定在前（0–11），自定义分类可拖拽（从 12 起编号）。

**问题**：系统分类不能排序。若你想「常用的放前面」，建议放开**统一排序**：
系统分类与自定义分类一起拖拽，只用标签区分「可删 / 不可删」。（这条不急，可以先放着。）

## 七、备份恢复的引用完整性（记一笔，以后做）

现状是物理删除（`DELETE FROM categories`）。
WebDAV 恢复备份时，如果备份里的物品引用了一个在新设备上已被删掉的分类，
物品就会显示成裸 id。

**建议**：恢复时遇到「物品引用了不存在的分类」，**自动补建该分类**
（label 取备份里的值）→ 数据自愈。属于后续优化，先记着。

7. 系统分类要不要也能拖拽排序？

## 附：本轮已修的问题（无需你决定，属于缺陷修复）

**现象**：在分类管理页点「删除分类」会直接失败。

**根因**：`CategoryDao` 里统计物品数 / 重挂物品的两条 SQL，
是按 `items.category` 这一列去匹配的。而这一列在 schema v3 的「逻辑删除」里
**已经从表定义中移除**（老库里物理列还残留，全新安装的库里根本没这列）。

**实测证据**（用 SQLite 直接跑那两条 SQL）：

| 场景 | 现有 `itemCount` / `unassignItems` | 修正后（改匹配 `category_key`） |
|---|---|---|
| 全新安装（v6，无 `category` 列） | ❌ `no such column: category` | ✅ 计数 = 2 / 影响 2 行 |
| 老库升级上来（`category` 物理残留） | ⚠️ 计数 = 1（**少算一半**），只重挂 1 件 | ✅ 计数 = 2 / 影响 2 行 |

**修复**：把匹配列从 `category`（中文名）改为 `category_key`（id），
并同步修正 `allItemCounts`、`CategoryManager.deleteCategory`（改用 `id` 而非 `label`）、
`category_page` 的计数调用点。

**顺带说明**：这也是为什么「物品只存 id」这个设计是对的 ——
如果当初存的是中文名，那么「改分类名」和「删分类」都会变成需要全表迁移的危险操作。
